# Speed

Part of the trainer manual (`../MANUAL.md` has the short version). Status: `verified` = run on the B580, `untested` = unit-tested in the sandbox only.

A step on this card is launch-bound (old measurement: ~22,300 kernel launches, ~48 us each; recompute adds ~7.5k).
So: fewer launches, fewer new shapes, fewer syncs.

| Lever | Switch | Effect | Cost | Status |
|---|---|---|---|---|
| Measured checkpoint placement | `trainer.tune_checkpointing=true` with `trainer.checkpoint_by=measured` | The probe's backward times each block's recompute and counts the memory of its activations; the blocks that save the most time per megabyte stop recomputing, residual blocks included, as far as the largest batch fits. Event `checkpoint_plan` lists the kept blocks with their MB and ms. | Same measuring pass as the share tuner, plus a timing synchronization per block in it. Keeps everything checkpointed when the profile shows no memory figures. | verified: batch 3, 512: 930 vs 1010 ms/step with the peak up from ~8.5 to ~10.5 GB; under a 10240 cap it emptied the cache after every step (1130 ms; fixed, retest) |
| Less recompute | `tune_checkpointing`, `attention_fraction` | Each skipped block's recompute is not run. | VRAM. | untested |
| LoRA in the activation dtype | `--param adapter.lora_compute=activation` (default `float32`) | The low-rank path runs in bf16 with the add fused into the matmul (`addmm`): no float32 copy of the input, no full-size float32 update cast back and added. The kernel profile of a native step showed about a quarter of device time in these casts and the float32 low-rank matmuls (the feed-forward projection to 10240 features spends more on its LoRA than on its base matmul). | The low-rank intermediate and the factors' gradient are rounded to bf16 (the factors stay float32 parameters; DoRA keeps float32). Loss comparison pending. | untested (TESTING 31) |
| Fused GEGLU | `--param trainer.fused_geglu=true` (needs xpu-kernels from a checkout) | The feed-forward activation runs as one fused kernel each way and the backward writes both halves of the gradient itself. | The kernel is verified against the eager chain first; a closed gate leaves the eager path with a warning. | verified: 5-8% faster, same loss |
| Channels-last convolutions | `--param trainer.channels_last=true` | Frozen convolutions and the UNet input keep the layout oneDNN runs without a reorder per call (about a tenth of the convolution time was reorders). | None known. | untested (TESTING 36) |
| Few shapes | `max_shapes` | First sight of a shape ~3.85 s; fewer shapes = fewer slow steps (the step line marks `new`). | Padding. | verified |
| Bigger batch | `--batch` | Launches are shared by more samples. | VRAM; use with `batch_area`. | verified |
| Conditioning store | `--persist-conditioning` / `conditioner.persist` | Second run neither loads encoders nor encodes. `conditioner.max_disk_mb` (4096) caps writes. | Disk. | verified: the second run skips encoding and starts sooner, same loss |
| Latent cache | automatic, next to the dataset | Encoded once per (`base`, `mode`, `max_aspect`, `step`). Cold build was ~108 s. | Disk. | verified |
| Latent encode batch | `latents.batch_size` (default 1) | Each distinct batch size compiles its own kernels; 1 is usually fastest overall. | - | verified (old tree) |
| Prefetch | `batcher.prefetch` (default 2) | Batches built ahead of the step. | Host memory. | verified |
| Fused/grouped optimizer | `fused`, `foreach`, `group_size` 0 | Fewer launches in the update (0 = all same-shaped at once). | `fused` no clipping. | measured: `--fused` ~1200 ms and `group_size=1` ~1200 ms against ~1010 ms default, memory the same: no gain for a LoRA |
| Graph replay | `--graph` / `trainer.graph=true`, `trainer.graph_shapes` (8) | After a shape has been seen 3 times (eagerly) its forward + loss + backward is captured as a device graph and replayed: the old tree measured about 2x (launch-bound step); the capture has to use the math attention (flash uses work-group scratch memory, which graph capture does not support), and in this tree on the B580 that cost 36% of the attention-heavy step's device time, so bf16 replay was slower than eager (1324 against 1134 ms at batch 4, 512) and int8 only slightly faster (1452 against 1550 ms). Each shape's replay is therefore timed against its eager warm-up steps and the graph is dropped when it is not at least 5% faster (a `[graph]` line says which). Graphs share one memory pool, so the cost is the largest graph (old tree: ~0.5-1.5 GB), not the sum. Captures with the math attention. | Needs: no dropout, no timestep gate, non-fused optimizer (all refused loudly); chunked batches, the probe, and shapes past `graph_shapes` run eagerly. Count shapes with `max_shapes`: each graph is a capture (seconds). Competes with `tune_checkpointing` for the same spare VRAM. | verified: replayed steps ~510-550 ms against ~1000 ms eager, same loss at step 40; shapes past `graph_shapes` ran eagerly (graphs now go to the most used shapes; raise `graph_shapes` if memory allows) |
| Graph attention | `trainer.graph_attention` = `math` (default), `math_bf16`, `chunked_bf16` | What the captured graph runs for attention (the fast kernel cannot be captured). The bf16 modes keep bf16 matrix products; `chunked_bf16` also keeps no score matrix. Scores are rounded to bf16 before the softmax. | Quality to check. | untested |
| Timing | `trainer.timing=true` | Per-phase times; synchronizes, so it slows a bit. Turn off for speed. | - | untested |
