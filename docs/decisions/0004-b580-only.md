# 0004 — Intel Arc B580 only; `xpu` hardcoded

## Context

The target machine has one accelerator: an Intel Arc B580. torch's XPU
backend is the only one that talks to it.

Everywhere a device is chosen, this codebase passes `"xpu"` — not a
default, not an environment variable, not a setting. There is no device
picker, and no code path that would produce `"cuda"` or `"mps"`.

The reason is worth keeping in the open, because it is *not* "we only have
one GPU". It is that the surrounding work is untested anywhere else: the
memory behaviour of the XPU caching allocator, the numerics of fused
optimisers on that backend, and the timing assumptions in the progress
and supervision paths were all developed against this device.

## Decision

`"xpu"` is hardcoded at the device boundary, with a comment saying why.
`backend/infrastructure/dataset_task_worker.py` is the clearest example:

```python
runner = DataTaskRunner(device="xpu")  # this project is B580-only
```

`fused-adafactor` and `xpu-adafactor` are offered as optimizer choices
because they are the ones that behave well here, and `xpu-adafactor` is
labelled as such in the config UI.

Model **directories** are *not* hardcoded — they resolve from ComfyUI's
layout by default, and `models_dir` / `WorkspaceDirs` redirect the whole
tree in one place. The dependency on another project's layout is a
configuration point, not an assumption (see `docs/setup.md`).

## Consequences

* **This does not run on another accelerator**, and the failure would not be
  graceful — `torch.xpu` would not exist.
* **No device option appears in the UI**, which is honest: offering a
  picker would imply the rest of the stack had been tried on the other
  values.
* Anyone porting this has to check the two places the device is chosen, and
  the assumption list above, before trusting it elsewhere.
* Hardware-specific work has been done on this machine: the streaming
  upload measurements, the memory figures in `docs/known-issues/open.md`,
  and the Adafactor trade all come from real runs on a B580.

## What pins it

* `backend/tests/test_config.py` — the config schema offers
  `xpu-adafactor` labelled "XPU Adafactor", and the Adafactor scale
  parameter appears for both Adafactor flavours but not for AdamW.

  This test did not exist when the record was first written; an earlier
  draft of this section cited a test that did not, which is the failure
  mode these records are meant to avoid. A decision with no test is a
  comment that will be edited.

* The device string itself is **not** pinned, deliberately. A test
  asserting `"xpu"` would fail the day this is ported — which is a change
  someone is making on purpose, and should be a small edit with the
  comment above as their guide rather than something a test forces them to
  work around. The cost of that choice is real: nothing will tell you the
  port happened, which is why the assumption list above is written down.
