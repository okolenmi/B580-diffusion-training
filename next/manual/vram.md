# VRAM (peak device memory)

Part of the trainer manual (`../MANUAL.md` has the short version). Status: `verified` = run on the B580, `untested` = unit-tested in the sandbox only.

Reading the numbers first. `device_used` is what the driver says for the whole card. Our share is
`process` (kernel per-client counter, Linux/xe). Other programs are `device_used - process` (measured here:
about 760-800 MB, flat). Inside our share, `allocated` is live tensors, `reserved` the allocator's cache (part of it
returnable), and the rest ("outside allocator") is context, compiled kernels and primitive scratch: 442 MB at
start, about 1.5 GB after the first forward/backward, creeping by ~4 MB per new shape.

| Lever | Switch | Effect | Cost / caveat | Status |
|---|---|---|---|---|
| Pixel budget per batch | `--batch-area X` / `buckets.batch_area` | Samples up to X times the base square's area run at full batch size; a batch holds at most `batch_size * X` base-areas of latent pixels in total (rounded down, at least 1 sample). Bounds the peak by pixels, not by shape luck. Example, batch 4, X 1.5, base 96x96 latents: a 96x144 sample (1.5x) runs batches of 4, 96x148 (1.54x) runs 3 (4*1.5/1.54), 96x192 (2x) runs 3 as well, 96x288 (3x) runs 2. | Smaller batches for big shapes = more steps per epoch for them; optimizer sees different effective batch sizes. 0 = off. | verified (batch 2, stable peak) |
| Fewer short batches | `--pack P` / `buckets.pack` (default 0.3; 0 = off) | Each shape's left-over samples (fewer than a full batch) are first moved into a larger existing shape's short batch, then combined into one batch in the smallest existing shape that holds them all, as long as no sample is more than P padding. Packing never creates a shape, so `max_shapes` still bounds how many the model meets. Short batches are slow the first time (their own kernels) and, with big batch sizes, many; this turns them into full ones. The batch-area limit still sets each shape's full size. Padding is masked out of the loss (see padding fill). | Padded samples cost the host shape's compute; attention and convolutions see the padding, so keep P modest. The remaining short batches are still a batch size of their own (a new compile each time they first appear); the `data:` line counts them. A batch is never larger than an existing one, so the peak does not rise. Different samples are packed every epoch. | verified: batch 8, 204 samples: pack 0 gives 34 batches with 14 short; 0.15: 29/3; 0.3 (default) and 0.5: 28/1, padding mean 5%, worst 29% |
| Few shapes | `--max-shapes N` / `buckets.max_shapes` (default 16) | Every new shape costs ~4 MB driver memory and several seconds of kernel compile the first time. Cheapest shapes are merged to a common padded size until at most N remain. Limit for 768 base, x2 max aspect, 4-latent padding multiple: 49. | Padding wastes compute in merged shapes (masked out of the loss). `padding_stats` and the `data:` line show the cost. 0 = no limit. | verified (8 shapes: ~7% mean padding; 49 or 0: ~2%) |
| Gradient checkpointing | `adapter.checkpointing` (CLI `--no-checkpointing` turns off) | Recomputes activations in backward instead of storing them: the biggest single saving. | ~+7.5k kernel launches per step; a launch-bound step gets slower. | verified |
| Share of blocks checkpointed | `adapter.attention_fraction` 0..1 | Fewer checkpointed transformer blocks = more activations kept = faster, more VRAM. Residual blocks always checkpointed. | Evenly spread blocks; fraction is a manual guess, see auto-tuner below. | untested |
| Auto checkpoint share | `trainer.tune_checkpointing=true` | Before step 1, measures the largest batch at several shares and picks the fewest-recompute share that fits the budget. Event `checkpoint_share`. | A few extra measuring passes at start. Use with an explicit `memory.vram_max_mb` for a margin. | verified (batch 1: share 0.75, 7% faster; batch 3 at 512 keeps 1.0); the cost estimate behind it was too pessimistic, now fitted from two probe sizes: retest |
| VRAM budget | `--set memory.vram_max_mb=N` (device-wide: other programs count) and `--set memory.margin_mb=N` (default 512) | One arithmetic everywhere: allocator cap = limit - what other programs and our non-allocator memory hold (measured) - margin. The checkpoint tuner, block placement and the batch planner use that cap, nothing added. The console prints it as `memory budget: ...`. A load that cannot fit (text encoders) is refused with the figures instead of failing inside the allocator. | Too tight = more splitting/slowness; margin too small = out of memory when a new shape first appears. `auto` = whole card. | reworked after test 4 (four stacked margins left a 10240 limit with about 7.6 GB for the trainer): retest 24 |
| Return allocator cache | automatic (`cache_returned` event); `--set runtime.empty_cache_every_n_steps=N` (default 1) | Gives free cached blocks back to the driver so the cache's creep (7.4 -> 7.9 GB seen) does not look like growth. | Re-allocation costs a little time; 0 never empties. | fixed: under an allocator cap the cache is no longer emptied every step (it cost ~20% when the placement used the whole budget) |
| Fused optimizer | `--fused` / `optimizer.fused` | Updates each parameter when its gradient is ready: gradients never pile up. | No gradient clipping when fused. | measured: no memory gain for a LoRA, ~1200 ms/step against ~1010 |
| Optimizer grouping | `optimizer.group_size` (0 = all same-shaped, 1 = one at a time) | 1 uses the least temporary memory. | Slower (more small launches). | measured: `group_size=1` same memory, ~1200 ms; with int8 state 2250 ms: do not combine |
| Optimizer state | `optimizer.state_precision=int8_blockwise` | State at about a quarter of the memory. | Small precision loss. Adafactor (`beta1` 0) keeps least state; CAME in between. | verified: int8_blockwise ~1030 ms/step, memory about the same (the optimizer holds ~84 MB at rank 16, gradients ~162 MB) |
| Int8 frozen weights | `--param adapter.base_precision=int8` (`adapter.int8_backend`, `adapter.int8_min_params`) | Linear layers of 1M+ weights (with a multiple of 256 inputs) keep their frozen weight in int8: about 2 GB less on SDXL, which buys batch size or fewer checkpointed blocks. Needs `pip install xpu-kernels` (without it a slow plain-torch version runs and a warning says so). | The model is the int8 network: losses and samples are not comparable with a native run. Measured on the card: ~1500 ms per step against ~1010 native (graph replay 1450: not launch bound). The input gradient now never builds the dense weight; run `scripts/bench_int8_layer.py` to see where the rest goes. DoRA layers stay native. | measured: 2059 MB saved, slower; retest 23 after the backward change |
| Adapter size | `--rank` / `adapter.rank` | Parameters, gradients and optimizer state scale with it. | Capacity. | verified |
| Fewer trained modules | `adapter.groups`, `include`, `exclude` | Fewer adapter parameters and less backward work. | Capacity/coverage. | untested |
| Encoders off the card | `conditioner.release_encoders` (default true) | Text encoders live on the host and visit the device only to encode. | Slower first epoch unless the conditioning store is on. | untested |
| Precision | `--set precision.denoiser/encoders/vae=auto|bf16|fp16|fp32`, `precision.autocast` | Lower precision = less memory. | fp32 is a big jump; quality risk with fp16. | untested |
| Accumulation instead of batch | `--accumulation N` | Same effective batch with the memory of one micro-batch. | More forward/backward passes; no larger batches' kernel efficiency. | verified |
| Allocator mode | env `PYTORCH_ALLOC_CONF=expandable_segments:True` | Could reduce stuck fragmentation. | Not known to work on XPU. | verified: peak 8.3 -> 7.1 GB, no speed penalty; now on by default (export `PYTORCH_ALLOC_CONF` to change) |

Not built (old tree had them, see `rework/71-memory.md`): NF4 frozen weights (measured 16-20% slower for
180-1361 MB; int8 above is the route now), block swap to host, activation offload.
