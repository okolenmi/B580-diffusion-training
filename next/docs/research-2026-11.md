# Research: optimisation math for training (Nov 2026)

What was looked for: newer math for the update itself (optimizers, LoRA parameterisation, multi-task weighting, averaging). The earlier survey (project doc `research-training-methods-2026-10.md`) covered timesteps, losses and adapters. Nearly all evidence below is LLM fine-tuning; diffusion evidence is thin or absent, so each item is a hypothesis for us.

## What the sources say

- **Schedule-free AdamW** ([The Road Less Scheduled](https://proceedings.neurips.cc/paper_files/paper/2024/hash/136b9a13861308c8948cd308ccd02658-Abstract.html)) removes the learning-rate schedule. In a U-Net DDPM benchmark ([Schaipp et al., arXiv 2510.19376](https://arxiv.org/abs/2510.19376), summarised on [emergentmind](https://www.emergentmind.com/open-problems/missing-lr-annealing-sf-adamw-generative-quality)) its loss matched AdamW's but the samples were worse, which the authors put down to the missing learning-rate annealing; a cooldown helped in some configurations. Not adopted: for generation the decay matters.
- **Post-hoc EMA** ([EDM2, Karras et al.](https://arxiv.org/pdf/2312.02696)): a power-function average of the weights, kept as two snapshots during training; any other averaging length is then reconstructed afterwards as a linear combination, so the length is tuned without retraining. No gain of its own; it makes the best length cheap to find. The same paper's learned loss weighting is uncertainty weighting over noise levels (the item already in the earlier survey); its magnitude-preserving layers need training from scratch.
- **FAMO** ([arXiv 2306.03792](https://arxiv.org/abs/2306.03792)): multi-task weights z = softmax(xi) updated from the change of each task's log loss, so every task's loss falls at about the same relative rate; O(1) cost, no per-task gradients. Same family as the time balance's `speed` mode; our gradient-norm scaling already does something similar, and our losses move only about 5%, so the signal would be noise. Low priority.
- **LoRA-RITE** ([arXiv 2410.20625](https://arxiv.org/html/2410.20625v2)): Adam gives different updates to the product B A depending on how it is factored, and in practice one factor moves much more than the other. A matrix preconditioner (polar decomposition of the other factor) makes the update invariant. About 5-8% slower than Adam on Gemma; +2.3 to 4.9% accuracy on LLM benchmarks; no image experiments. Matches our observation that Adam concentrates the change in a few layers; LoRA+ (a larger rate for B) is the cheap relative.
- **LoRA-One** ([arXiv 2502.01235](https://arxiv.org/abs/2502.01235v1)) and LoRA-GA / LoRA-Pro: initialise the adapter from the top singular subspaces of the full gradient of the first step(s) instead of at random; LLM tasks only, no numbers seen. Close to our "first steps set the direction" result.
- **Learning rate against rank** ([arXiv 2602.06204](https://arxiv.org/pdf/2602.06204)): with a random A and B = 0, the stable rate falls as rank^(-1/2) when the scaling alpha is fixed, and is rank-invariant when alpha follows 1/rank; includes one Stable Diffusion 1.5 check (naruto captions): rank-invariant optimum with alpha = 1/rank. For us: do not reuse a learning rate when the rank changes.
- **Batch size and LoRA** ([arXiv 2602.09492](https://arxiv.org/abs/2602.09492)): the best learning rate rises and then falls with batch size, batch size alone moved accuracy by more than 10%, and conflicting results between LoRA variants come mostly from untuned batch sizes. For us: every pass so far had one image.

## What I would try, in order

1. **Several images per pass** (TESTING 52, no build). Regions run as separate passes at batch 1, which is probably bound by kernel launches, so 2-4 images per pass may cost far less than 2-4 times as long, and it answers the batch-size point above.
2. **Long run with and without decay** (TESTING 53, no build), later with an adapter EMA (small build: 160 MB per average).
3. **Gradient-aligned A** (medium build): with B = 0 the function does not change, so only A can be set from the gradient: the top right singular vectors of the full gradient of each adapted layer, accumulated over several batches with all regions. The gradient can be streamed into a randomized SVD per layer (a forward hook keeps the layer input, a backward hook the output gradient; the sketch G times a random matrix of width rank+8 costs a few percent of the layer's own work and a few MB per layer), so the full weight gradients (a few GB) are never stored. Fits the first-steps result; no diffusion evidence for it.
4. **LoRA+ rate ratio** (small build: the optimizer groups already have a multiplier) before anything as heavy as LoRA-RITE.

Nothing found changes the picture that the large gains came from how the training signal is composed (timesteps per image, equal gradient size per region, the first steps), not from optimizer math.
